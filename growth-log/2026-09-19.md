# Growth Log

## Tenant Context Propagation: JWT claims must carry org_id, not just header

### Context
- Transforming single-user auth into multi-tenant B2B SaaS auth system
- Initially designed org context to come only from `x-org-id` header, with JWT as fallback
- Realized during implementation that this creates a fragile dependency: if the frontend forgets the header, all org-scoped queries silently return wrong data (empty or first-org)

### Root Cause / Core Insight
- Tenant isolation must be **implicit in the token**, not **explicit in the request**
- If the frontend must remember to add a header for every API call, you've distributed a critical security invariant across N call sites
- JWT claims should carry the active org context so the backend can always resolve tenant without relying on client behavior
- The `switch-org` endpoint returning a new token (not just the org data) is what makes this work: every org switch refreshes the token's org claim

### The Pattern (transferable)
- Next time implementing multi-tenant auth, I will put the tenant context in the JWT claims first, and use headers as a secondary override mechanism (not the primary)
- Signal to recognize: when you're adding `x-org-id` headers in multiple frontend call sites, you've distributed the tenant context instead of centralizing it
- The fix: `authHeaders()` in AuthContext sends both the token AND the header, but the backend validates from the token first

## Python string escaping breaks template literals

### Context
- Writing OrgSettings.tsx via Python script (`python -c "..."` with heredoc-style content)
- Template literals like `${API_BASE}/api/organizations/${organization.id}/members` got mangled by Python's string processing
- Backticks were lost, dollar signs were escaped, resulting in TypeScript compilation errors

### Root Cause / Core Insight
- Python's raw string handling (`r'''...'''`) doesn't understand JavaScript template literal syntax
- The `\${}` inside Python strings gets interpreted or stripped differently than JS expects
- Writing JSX with template literals through Python is unreliable

### The Pattern (transferable)
- Next time writing TSX files from Python, I will either: (a) use the `write` tool directly instead of Python, or (b) use string concatenation (`'${' + var + '}/...'`) in the Python output instead of template literals
- Signal to recognize: when you see `error TS1127: Invalid character` on template literal lines in a file you generated via Python, the escaping is broken

## Vercel nested routes require explicit rewrites for serverless functions

### Context
- Creating `/api/organizations/:id/members` endpoint
- Vercel doesn't automatically route nested paths to the parent file
- Had to add explicit rewrites in `vercel.json` to forward `/api/organizations/:id/members` to the `organizations.ts` handler

### Root Cause / Core Insight
- Vercel's file-based routing maps `/api/organizations.ts` to `/api/organizations`, not `/api/organizations/*`
- For nested resources, you need either: (a) explicit rewrites in `vercel.json`, or (b) a separate file that imports the parent handler
- The rewrite approach is cleaner: `organizations-members.ts` imports `handleMembers` from `organizations.ts`

### The Pattern (transferable)
- Next time adding nested API routes in Vercel, I will immediately check if the nesting requires explicit rewrites or a separate handler file
- Signal to recognize: when you have `/api/[resource]/[subresource].ts` pattern, verify it works with Vercel's routing before writing the handler
- The shortcut: create a thin proxy file that imports and delegates to the parent handler
